Hit or Miss: modelling a choice with enum

From “A and B” to “A or B”. One enum. ~20 minutes.

Last lesson you modelled a Monster as immutable data: a name and an armorClass, bundled together. That “and” makes it a product type. Today we model the other half of the shape space — a choice. When the Dice Oracle resolves an attack, the result is a Hit or a Miss: never both, never neither. A value that is “one of a fixed set of alternatives” is a sum type, and Scala spells it enum.

Product vs sum — the whole idea in one line

A product type combines fields: a Monster is a name and a number (case class). A sum type offers a choice: an outcome is a Hit or a Miss (enum). Almost every domain you'll ever model is built by nesting these two — “ands” and “ors” — all the way down. Together they're called algebraic data types (ADTs). [Scala 3 Book: ADTs]

The tool: enum

enum AttackResult:
  case Hit(damage: Int)
  case Miss

Read it literally: an AttackResult is either a Hit (which remembers how much damage it dealt) or a Miss (which carries nothing — a miss is just a miss). You build each case by name: 

val crit  = AttackResult.Hit(6)
val whiff = AttackResult.Miss

This is not a C# enum

The keyword is the same, so here's the trap to avoid. A C# enum is just a set of named integers — Hit and Miss would secretly be 0 and 1, and neither could hold any data: 

// C#: enum AttackResult { Hit, Miss }   — just named ints, no payload

A Scala enum case can carry its own data — that's why Hit(damage: Int) works and Miss doesn't need to. That makes it a discriminated union: the feature you may know from F# or TypeScript, and the one C# still lacks natively. If you've ever reached for a clumsy enum + switch + a-bag-of-nullable-fields to fake “a hit has damage but a miss doesn't,” this is the clean tool you were missing. [Scala 3 Book: Enums]

Why sum types matter

Make illegal states unrepresentable

Because an AttackResult is exactly one case, you literally cannot construct a nonsensical “a hit that also missed,” or “an outcome that's neither.” In the mutable-flags world you might model this as bool WasHit plus int? Damage — and then have to hope every code path keeps them consistent. A sum type deletes that whole class of bug by construction: the impossible states simply have no way to exist.

There's a second payoff you'll cash in next lesson: because the compiler knows the complete, finite list of cases, it can check that you've handled every one when you branch on a result. Model the choice precisely today, and the compiler becomes your safety net tomorrow.

Do it: a combat log

1

Create the file

Make attacks.scala with this:

enum AttackResult:
  case Hit(damage: Int)
  case Miss

@main def combat() =
  val log = List(
    AttackResult.Hit(6),
    AttackResult.Miss,
    AttackResult.Hit(3)
  )
  println(log)
2

Run it

scala-cli run attacks.scala

You should see the whole log print, each case showing its data (or lack of it):

List(Hit(6), Miss, Hit(3))

Notice a List can hold a mix of Hits and Misses happily — they're all AttackResults. And, just like a case class, each case prints its values instead of a memory address.

3

Your turn (the win)

Extend the model — this is the move you'll make constantly in FP:

  • Add a third case to the enum: case Critical(damage: Int) — a critical hit.
  • Add a Critical(12) to your combat log and re-run.

It just works, and the printout grows to include Critical(12). Pause on how cheap that was: one line to add a whole new outcome to your domain, and every existing AttackResult value is still valid.

Milestone

You've modelled a choice as data — the second of the two building blocks (product + sum) that every domain model is made from. The Dice Oracle now has both a monster to hit and a way to say whether the hit landed.

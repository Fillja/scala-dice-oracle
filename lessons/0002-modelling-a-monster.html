FP in Scala · Lesson 2

Modelling a monster with immutable data

Your first brick of the game domain. One case class. ~20 minutes.

Our mission is a Dice Oracle that resolves attacks against monsters. Before any dice roll, we need a monster to attack. Today we model one — and we do it the functional way: as immutable data. This is the single most important habit to build first, because every later lesson (attack resolution, the network protocol) rests on it.

The tool: case class

A case class is Scala's way to say “this is a small bundle of data.” Think of the C# classes you already write — but with the functional defaults flipped on: no setters, and equality compared by value instead of by reference. (That's exactly what a C# record gives you; but if you've mostly written mutable { get; set; } classes for EF, the setter-free part is the real shift.) 

// Scala 3
case class Monster(name: String, armorClass: Int)

// The mutable C# class you'd write today:
//   public class Monster { public string Name { get; set; } ... }
// The case class above is that — minus the setters, plus value equality.

That one line is a product type: a Monster is a name and an armorClass, bundled together. From it, the compiler generates a surprising amount for free [Scala 3 Book: Domain Modeling Tools]:

  • A constructor you call without new: Monster("Goblin", 15).
  • Public fields that are immutable — they're vals, so name and armorClass can never be reassigned.
  • Value equality: two monsters with the same fields are ==. (A C# class would compare by reference; a record compares by value, just like this.)
  • A readable toString — printing one shows Monster(Goblin,15), not a memory address.
  • A copy method to derive a changed version without mutating the original. More on this below.

Why immutable? (the part that matters)

Coming from C#, your instinct — honed on { get; set; } classes — is probably: “fine, but why can't I just set armorClass later?” Here's the payoff, and it's the heart of FP.

Immutable = no spooky action at a distance

A setter is a handle for changing an object after you've handed it out. Pass the same mutable Monster to two parts of your program and either one can call that setter — leaving the other silently surprised. That's aliasing, and it's a classic source of bugs. A case class simply has no setter: once built, a Monster can never change, so you can share it freely — across functions, threads, or (soon) both ends of our network protocol — knowing nobody can mutate it out from under you. [Scala 3 Book: val is immutable]

One place mutability still earns its keep

Your EF entities are mutable on purpose: change-tracking needs those setters to diff your object and generate the UPDATE. That's the one layer where mutable classes are the right call — and it's fine. But notice what we're modelling here: a monster, an attack outcome, a message on the wire. That's the value world (your DTOs and view models), not the change-tracked-entity world — and it's exactly where immutable data shines.

There's a second, subtler win. Because a Monster value is frozen, Monster("Orc", 13) means exactly “an Orc with AC 13” — nothing more, nothing hidden, no history of who mutated it. A function that takes a Monster and returns something will give the same answer every time for the same monster. That property — same input, same output, no surprises — is called referential transparency, and it's the reason functional code is so easy to reason about and test. We'll lean on it hard when we write the attack-resolution logic.

The mental flip

OOP asks “what can this object do, and how does its state change over time?” FP asks “what is this value, right now, forever?” A case class is a value, not a mutable thing. Hold that thought — it's the whole shift.

Changing without mutating: copy

“Frozen forever” sounds impractical until you meet copy. You don't change a monster — you derive a new one and leave the original untouched: 

val goblin  = Monster("Goblin", 15)
val armored = goblin.copy(armorClass = 17)

// goblin  is still Monster(Goblin,15)  — unchanged
// armored is       Monster(Goblin,17)  — a brand-new value

Where you'd reach for a setter, you reach for copy instead. (It's the same idea as a C# record's goblin with { ArmorClass = 17 } — a with-expression, not an assignment.) The old value survives; you just made a new one alongside it.

Do it: build the roster

1

Create the file

In your project folder, make monsters.scala with this: 

case class Monster(name: String, armorClass: Int)

@main def roster() =
  val monsters = List(
    Monster("Goblin", 15),
    Monster("Orc",    13),
    Monster("Dragon", 18)
  )

  // Look one up by name.
  val found = monsters.find(m => m.name == "Orc")
  println(found)
2

Run it

scala-cli run monsters.scala

You should see:

Some(Monster(Orc,13))
What's that Some(...)?

find can't promise a match exists, so it returns an Option — Some(monster) if found, None if not. That's Scala being honest about “maybe nothing” instead of handing you a null. Don't worry about unwrapping it yet — Option gets its own lesson soon. For now, just notice the wrapper.

3

Your turn (the win)

Make two small changes and re-run:

  • Add a fourth monster — a Skeleton with armor class 13 — to the list.
  • Change the lookup to find your Skeleton instead of the Orc.

Then, as a one-line experiment, add this and run again: 

println(Monster("Orc", 13) == Monster("Orc", 13))

It prints true — two separately-built monsters are equal because their values match. That's value equality, for free, and it's exactly what makes monsters easy to compare and test.

Milestone

You've modelled a piece of the game domain as immutable data, built a roster, and looked a monster up by name. This is the functional core taking shape.
